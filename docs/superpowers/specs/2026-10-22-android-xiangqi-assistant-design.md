# 安卓本地象棋分析助手设计

日期：2026-10-22（北京时间）

目标设备：iQOO Neo9S Pro+

状态：聊天方案及本文均已由用户确认；实施计划另见 `../plans/2026-10-22-android-xiangqi-assistant.md`。

## 1. 目标与成功条件

用户在安卓手机的 JJ 象棋人机模式中自行落子。助手取得用户授权后持续读取棋盘，在手机本地调用高水平象棋引擎，显示当前局面的推荐走法。首版交付可安装的 ARM64 APK、对应源码及构建说明。

用户已确认：纯手机运行，Pikafish＋NNUE 本地分析，自动识别并允许校准，过滤动画，悬浮箭头和文字提示，跟踪连续对局并处理悔棋及重开。

棋力目标是充分利用目标手机进行可靠的本地分析。“绝对最强”、战胜所有对手、固定搜索深度或胜率不作为可保证指标。推荐必须来自当前已确认局面的引擎搜索；识别有歧义时停止给出新走法。

## 2. 已有证据与适配范围

用户提供了 `a6a8e0be1bfc650b00696209446b7cd0.mp4`。文件约 29 秒，画面为 576×1280、30 帧/秒，共 870 个视频帧。已人工检查抽取的开局和中盘关键帧，尚未完成程序识别或真机测试。

画面特征：

- 竖屏、木质圆形棋子、红黑书法字，开局帧包含双方全部 14 类棋子。
- 当前录像中红方在下；棋盘包含 9 列、10 行交点。
- 交点约为 `x = 41 + 63.2 × 列`、`y = 367 + 60.3 × 行`。这只用于录像标注；运行时重新定位和校准，不能固定使用录像像素坐标。
- 吃子时出现覆盖多个交点的大型“吃”字动画，另有棋子选择光圈、落点光圈和手指触点。
- 棋盘下方有悔棋、翻转、重来等按钮；悬浮控制面板应放在上方装饰区域并支持拖动。

首版支持此录像所示的 JJ 棋盘主题、竖屏布局及双方朝向。实际屏幕分辨率通过坐标变换适配。更换棋子皮肤、横屏和其他象棋应用不列入首版验收；遇到不匹配主题应提示重新校准，不能继续输出未经验证的推荐。

目标构建范围为 Android 10/API 29 及以上、`arm64-v8a`。使用 API 36 编译和目标平台、JDK 21、NDK 28.2.13676358；Gradle/Android Gradle Plugin 的兼容版本在实施计划中锁定。目标手机的实际系统版本、录屏会话行为、温度和分析速度必须通过真机验证。

## 3. 使用流程

1. 打开“象棋分析助手”，查看引擎是否就绪，选择我执红或执黑以及思考时间。
2. 开启系统悬浮窗权限，并通过系统界面授权本次录屏。系统支持时，优先选择只捕获 JJ 象棋。
3. 切入 JJ 的人机对局。助手定位棋盘并展示已识别局面的缩略校验图；用户确认朝向和当前行棋方。标准开局默认红先，任意中盘不凭单帧猜测行棋方。
4. 自动定位失败时，用户标记棋盘两个对角交点并确认朝向；识别错误可在助手的棋盘编辑界面修正。
5. 识别结果通过稳定性和规则校验后开始分析。我方行棋时显示可执行的推荐；对方行棋时清除我方箭头并显示等待状态。
6. 用户自行落子。新局面出现后旧搜索被取消，旧箭头立即失效；确认对方走棋后再次分析。
7. 用户可通过小窗或常驻通知暂停、重新校准、调整思考时间和停止。停止后释放录屏、悬浮窗及引擎资源。

首次需要完成系统授权；以后每次录屏会话仍遵循系统授权要求。手机锁屏、系统结束捕获或进程被回收后，显示停止状态并要求重新启动会话。

## 4. 架构与职责

采用 Kotlin 安卓应用，加 JNI 原生引擎。界面、录屏前台服务和识别协调器在应用主进程，引擎在独立 `:engine` 服务进程。

数据流：

`MediaProjection → ImageReader → 棋盘定位/校准 → 90格识别 → 稳定性及规则校验 → 已确认局面与走棋历史 → 引擎服务 → 版本校验 → 文字/箭头`

模块职责：

| 模块 | 输入与输出 | 依赖和约束 |
| --- | --- | --- |
| 配置和控制界面 | 权限、执棋方、校准、思考时间、暂停/停止 | 用户可校正识别结果，不要求无障碍权限 |
| 捕获服务 | 系统授权 → 带时间戳的最新画面 | 前台通知、生命周期和捕获尺寸变化 |
| 棋盘识别器 | 画面和主题模板 → 90个格点标签及置信信息 | 不自行决定行棋方，不把动画当棋子 |
| 对局跟踪器 | 识别候选＋规则校验 → 确认局面、历史、状态版本 | 唯一真实局面来源，负责漏步与重新同步 |
| 引擎网关 | 局面、历史、预算 → 搜索进度和最佳走法 | Binder IPC，进程死亡可恢复，搜索串行管理 |
| 悬浮显示 | 当前有效结果和棋盘坐标映射 → 面板与箭头 | 不遮挡 JJ 操作，不接受旧局面的结果 |

所有图像处理均在工作线程完成；只保留最新待处理帧，不能排队分析过时画面。初始采样目标为每秒 3 帧，暂停及停止时停止采样。实际采样频率由性能验证调整，不影响结果版本校验。

## 5. 棋盘识别与局面跟踪

### 5.1 定位、分类与校准

自动定位利用棋盘网格和矩形边界，检测失败时使用手动校准。采用归一化棋盘坐标；显示尺寸、捕获区域、旋转或朝向变化后重新建立坐标变换并隐藏旧箭头。单应用捕获的画面边界与屏幕位置分别记录，不能假定二者原点相同。

首版采用针对已提供主题的棋子模板匹配，结合红黑颜色特征识别双方的 7 类棋子及空位。模板取棋子内部区域，减少木质外圈、阴影及光圈的干扰。先用录像开局样本建立模板，再用其他稳定帧验证；不能用模板来源帧上的自匹配结果代表实际识别率。

每个交点均输出候选标签和置信信息。低置信、模板不匹配、遮挡、棋盘缺失或不合理棋子数均不生成确认局面。全局规则仅用来排除候选，不能凭“看起来像合法走法”补造被遮挡的棋子。

手动校正界面允许对格点设置棋子或空位、设置当前行棋方和确认朝向。非法局面必须说明原因并阻止分析。

### 5.2 稳定性、合法走法与历史

初始稳定标准为至少 3 个连续采样帧产生相同的完整格点分类，并且棋子内部区域没有显著运动或遮挡。阈值通过录像中的稳定段、动画段及压缩噪声标注校准，不能通过降低阈值来绕过识别失败。

稳定性不能只比较整幅截图：背景火光、装饰和头像动画不应阻止正常分析。选中光圈也不等同于棋子移动。棋子离开已确认位置、棋盘变换或大动画开始时撤下旧推荐，保留上一个确认局面供同步使用。

合法走法由 JNI 暴露的同版本 Pikafish 规则接口生成，识别器和 Kotlin 界面不另行实现一套不同的完整象棋规则。对局跟踪器将候选棋盘与当前局面的合法后继比较：

- 相同棋盘：不重复启动搜索。
- 唯一合法单步变化：追加走棋历史，切换行棋方，递增局面版本。
- 与历史中的已确认局面相符：识别为悔棋候选，确认后截断历史并恢复相应行棋方。
- 标准初始布局重新出现：作为重开候选确认，并重置历史。
- 仅画面朝向变化：更新坐标变换，保留棋子身份与历史。
- 漏步、多步跳变、摆盘、歧义或非法变化：暂停推荐，展示重新同步入口，不猜测中间走法。

FEN 内的红黑身份、当前行棋方和屏幕上下方向是三个独立字段。历史保存为起始 FEN 加完整走法序列。

从开局连续跟踪时保留完整重复局面信息；中途加入或人工重新同步时标记“历史不完整”，明确长将、重复等历史规则分析受限。引擎规则与 JJ 的具体裁决不能默认完全一致。

## 6. 本地引擎与资源管理

使用官方 Pikafish 源码和匹配的 NNUE，通过 APK 内的 JNI 库运行。权重在构建时准备并随应用提供，安装后分析不依赖联网。不要把引擎写入应用可写目录再当独立可执行文件启动。

构建记录必须包含：引擎完整提交 SHA、NNUE 原始来源与 SHA-256、工具链版本和编译参数。两个版本必须分别固定。权重下载保留 TLS 验证；不可直接使用上游下载脚本中关闭 TLS 校验的后备路径。应用首次装载及权重异常时检查文件完整性，失败则停止引擎初始化。

只构建 ARM64。提供 ARMv8 基线库和 dot-product 优化库，运行时检测 CPU 能力后只装载一种；不能在未检测的设备上执行扩展指令。原生库满足 Android 16 KB 内存页兼容要求，并通过构建检查。

初始默认值为 4 个搜索线程、256 MiB Hash、`MultiPV=1`、单步 15 秒；界面提供 3、15、30 秒档位。线程不超过设备可用逻辑核数；内存不足时停止搜索并降低到 2 线程、128 MiB Hash 后提示用户重试。Hash 不代表应用总内存占用。

低延迟档和深度档只是不同的搜索预算，不能承诺固定深度。温控提示或持续性能下降时允许用户降档；严重热状态自动暂停搜索并清除箭头，恢复后由用户继续。

### 6.1 并发和结果有效性

每个搜索携带 `sessionId`、`positionRevision`、`searchId`、`transformRevision`；返回的进度及走法必须关联发起时的值。当前会话、局面或坐标变换不匹配时直接丢弃结果。

引擎管理器串行执行初始化、修改设置、切换局面、搜索和销毁。`stop` 只表示发出取消请求；必须等旧搜索实际结束，才能设置新局面、修改线程/Hash 或开始下一次搜索。等待放在引擎工作线程，不能阻塞 Android 主线程。

新局面到来后立即隐藏旧箭头，再取消旧搜索。最佳走法先检查格式、格点范围及在当前确认局面中的合法性，然后才可显示。终局无合法走法、搜索失败、初始化失败和识别失败分别显示，空结果不能转换成箭头。

引擎进程崩溃、初始化超时或 Binder 断开时清除显示并进入可重试状态。停止搜索超时可以重启本应用的引擎服务；恢复后重新装载最近已确认局面，所有旧回调继续失效。

## 7. 录屏、悬浮显示与系统生命周期

捕获使用 MediaProjection 和 ImageReader，由 `mediaProjection` 类型前台服务维持。声明所需的前台服务及录屏权限；先取得本次系统授权，再启动捕获。注册停止回调；Android 14 及以上不复用旧授权或同一会话创建第二次录屏。

悬浮窗使用系统悬浮窗权限和 `TYPE_APPLICATION_OVERLAY`。文字控制面板默认位于录像顶部的装饰区域，支持拖动、折叠和暂停。面板不覆盖棋盘或 JJ 的底部按钮。

棋盘箭头层不接收触摸；Android 12 及以上将该层窗口透明度限制在系统触摸遮挡阈值以内，并通过真机验证点击穿透。不可只设置 `FLAG_NOT_TOUCHABLE` 就宣称不会挡住 JJ 操作。多个悬浮层的合成遮挡也需要检查。

优先采用系统单应用捕获，验证录制的 JJ 内容不含助手悬浮层。全屏捕获时，在识别采样前暂时隐藏箭头，等待至少两张隐藏后新生成的捕获帧，再做棋盘识别，随后恢复仍然有效的提示；控制面板始终位于棋盘外。不能把助手自身的 `FLAG_SECURE` 当作通用的悬浮层排除方案。

录屏区域变化、屏幕旋转、系统切换捕获内容、锁屏和权限撤销均令当前坐标映射失效。目标应用画面被系统保护而无法获取时，显示明确的不支持状态并停止分析，不输出猜测局面。

停止会话时释放 VirtualDisplay、ImageReader、MediaProjection、悬浮窗口、任务队列和引擎绑定，并终止搜索。应用不请求无障碍权限，不替用户点击落子。

## 8. 交付、数据与许可

交付物包括 APK、安装与授权说明、固定版本的构建说明、测试结果和已知限制。APK 使用本地开发签名供安装验证；签名私钥不能提交到 Git。

图像和局面分析在手机本地完成。默认不保存整屏录像、不上传屏幕或棋谱；仅持久化用户设置、校准和用于恢复的局面历史。显式导出诊断时，只导出棋盘裁剪和必要日志。

原始用户录屏保留在当前工作区附件目录，不把含头像等界面的完整录像提交到仓库。识别测试使用后续人工挑选、裁剪到棋盘并标注的样本；明确样本来自用户提供的适配素材，不宣称拥有 JJ 美术资产版权。

由于 JNI 链接并分发 GPLv3 Pikafish，应用/JNI/引擎集成按 GPLv3 提供对应源码、许可证和修改说明；同时核实并记录所用 NNUE 的许可与分发条件。每个 APK 的构建清单对应确定的源码和权重版本，提供重建所需的说明和补丁。

## 9. 验证与验收

### 9.1 云端可验证项

1. 能从干净的依赖安装流程构建 ARM64 APK；固定工具版本、权重校验和原生库页大小检查通过。
2. 以人工标注的开局样本核对全部 90 个交点，其中 32 枚棋子及空位全部正确；另选未用于模板提取的稳定帧验证全部 90 个交点。
3. 标注录像中的多个稳定局面和过渡区间；稳定局面识别与标注一致，吃子动画期间不生成伪局面，结束后能恢复。
4. 规则测试覆盖马腿、炮架、将帅照面、被将军后的应将、双方走向和终局；与冻结的已知局面预期核对。
5. 引擎装载匹配权重后完成搜索，返回当前局面的合法走法；损坏或缺失权重会明确失败。
6. 搜索进行中切换局面、翻转、悔棋、重开、停止及进程断连时，旧进度和旧最佳走法均不能再次出现。
7. 校准映射、双方朝向和单应用捕获尺寸变化下，箭头起终点与目标交点一致。
8. 有完整历史与中途恢复两类测试，确认历史不完整时不伪造重复局面信息。

云端引擎功能测试可使用相同提交及权重的宿主机测试程序。安卓 JNI 装载、Binder 连接和完整捕获服务需要在安卓模拟器或真机执行；宿主机程序通过不能替代这些检查，未执行项必须单独列明。

不能把模板来源帧上的自匹配、零测试执行、仅有成功构建或引擎进程存在当作功能通过。

### 9.2 必须在目标手机验证项

1. 在 iQOO Neo9S Pro+ 安装 APK，走完授权、切入 JJ、校准、分析及手动落子的完整流程。
2. 至少连续完成双方各 5 次落子；覆盖吃子、悔棋、翻转和重开，录像记录局面与提示是否同步。
3. 显示箭头时正常点击棋子和目的格，顶部小窗不挡 JJ 按钮；确认悬浮图形不会被当成棋盘内容再次识别。
4. 验证录屏停止、锁屏、权限撤销、切换应用后的清理和重启；确认 OriginOS 没有无提示终止必要服务。
5. 默认档持续运行至少 15 分钟，记录分析时间、搜索节点速度、应用内存、温度状态和耗电变化；据此校准默认线程与 Hash。

云端测试通过后可以交付待真机验证的 APK。只有完成真机流程后才宣称 JJ 实时辅助在目标设备上验证通过。

## 10. 实施顺序与本轮边界

本文确认后编写实施计划，依次实现：原生引擎和规则接口、录像样本与识别跟踪、安卓捕获和悬浮控制、完整集成与验证。每阶段保留可独立检查的输入输出，先验证正确性再优化速度。

本轮开始时云端仓库为空，尚未安装 Android SDK/NDK，也没有产品代码、识别程序或 APK。JDK 21 可用。设计文档确认后再按实施计划准备构建环境；不会把文档确认当作已完成功能。
